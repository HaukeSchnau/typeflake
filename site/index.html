Nix modules in TypeScript, typed by your own configurations.

Typeflake reads the option graph of your NixOS, nix-darwin and Home Manager configurations with nix eval and generates TypeScript types from it. You write modules in Effect TypeScript against those types, and Typeflake renders each one to an ordinary .nix file next to it. That file builds with Nix alone.

Early alpha The probe, the type generator, module rendering and the CLI work. A first port of infra's app-stores module builds the same drvPath as the original on srv-2 and m1.

One host, 41,038 options

srv-2 is a NixOS server in infra, the repository Typeflake is first built for. Its configuration has 41,038 options once Home Manager's are counted, and 35,962 of them are visible in the manual. They come from nixpkgs, Home Manager, disko, sops-nix and infra's own modules, at the versions flake.lock pins.

Typeflake turns them into 5.9 MB of TypeScript, leaving out only the hidden ones. A typo in an nginx location, a sops-nix mode written as a number or a Home Manager state version that doesn't exist then fails in the editor, before Nix evaluates anything.

From option graph to plain Nix

  1. Probe the option graph

    Works today

    src/probe.nix walks a configuration's options with builtins only and prints the tree as JSON. It reads the module system's type metadata, such as nested types, enum values and submodule options, and never parses descriptions. srv-2 takes 11 seconds.

    Shell
    srv-2.json One option, as the probe prints it

  2. Generate types

    Works today

    src/Typegen.ts turns the tree into interfaces that describe evaluated values. Groups and submodules become interfaces named after their first option path, and identical ones are shared. An option's description becomes its JSDoc, so the editor shows it on hover. typeflake types nixosConfigurations.srv-2 runs the probe and the generator and writes the result into .typeflake/.

    options.ts An excerpt of what the generator wrote

  3. Write a module

    Works today

    A module is a *.nix.ts file like the one at the top. Generated declarations augment a Register interface, so NixOS.module(…) is typed without annotations. The first port typechecks against srv-2's types in 0.77 seconds, and four mistakes injected into it all fail.

  4. Render it to Nix

    Works today

    typeflake render writes each module's .nix file next to it, and --check fails when one is out of date. Your flake.nix imports the result like any other module. Delete the .ts files and the repository still builds.

  5. Check the port

    Done for app-stores

    A port must not change what any host builds. For app-stores, each host swapped the module once for a copy of the original and once for the rendered port, and both printed the same drvPath, on srv-2 and on m1.

Rules it keeps

  • Nix stays the build

    Generated Nix builds with Nix alone, without Node, Bun or a Typeflake Nix library. Typeflake is a way to write .nix files, not a runtime.

  • Types come from your configurations

    They are probed from the flake you already have. There is no hand-written schema to fall behind nixpkgs.

  • No any

    Every Nix expression has the type of the value it evaluates to, Nix<T>. Option types Typeflake can't map yet stay visible as Unsupported<"name">. About 240 option positions do today, across 25 custom types, and 152 of them are nixpkgs' systemd option.

  • A port changes nothing

    Porting a module leaves every host's system.build.toplevel.drvPath as it was. That is the test for every port.

Where it stands

Works today

  • The option probe on NixOS and nix-darwin hosts, with Home Manager's options from the same NixOS probe.
  • The type generator, and typeflake types to run both for a host.
  • Modules: NixOS.module, Options, nix`…`, mkIf and the proxies for config, lib and pkgs.
  • typeflake render, with --check for drift.
  • A first port of infra's app-stores module, with an unchanged drvPath.
